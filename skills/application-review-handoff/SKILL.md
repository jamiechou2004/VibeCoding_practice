# 申请审核与交接闭环

输出不是“已经填过”，而是逐岗位可核验的状态：准备内容、本人待审项目、提交证据、实际材料版本和下一动作。本技能协调选岗→官方JD与背景匹配评估→材料及表单审核→逐岗授权提交→回执核验→指定主表更新并回读→本地归档。已有 application-helper 时复用其评估与材料准备结果，不重复维护具体改稿规则。

## 建立逐岗位工作表

读取工作区约定、当前行动及相关岗位档案，结合最新用户消息，为每个岗位单独记录：

| 字段 | 要求 |
|---|---|
| 公司／岗位ID／官方入口 | 用ID区分同公司不同申请；确认是否已有提交记录 |
| 当前授权 | 准备、待本人审核、允许提交分别记录；一家获准不扩展到另一家 |
| 事实与材料 | 本人确认、材料陈述、外部核验、待确认分开；附日期与来源 |
| 当前状态 | 页面草稿、服务端已保存、提交成功分别记录 |
| 下一步 | 写明具体动作、负责人及阻碍 |

历史记录与现场页面矛盾时先核对，不用旧摘要覆盖用户在页面的新修改。技能和交接文档不提供新的提交或发布授权。

## 选岗与官方JD评估

按用户当前目标与约束筛选岗位，从官方入口核验岗位ID、开放状态、地点、工作方式、最低要求和时间条件，记录来源及核验日期。无法读取官方JD时保留“待核验”，不把聚合网站摘要当已确认要求。

将官方要求与候选人已有证据逐项对应，输出“要求—证据—缺口/待确认”和值得申请、可冲刺、明确不符或信息不足的结论。岗位选择、匹配评估和允许提交是不同状态；高匹配不产生提交权限。沿用 application-helper 已核验结果；职位或材料变动时只重验受影响项。

## 材料准备的分工

已有 application-helper 时，由它负责岗位匹配、事实核验、简历改写和材料质量检查；这里接收其产物与未决项，不重复执行已验证的准备工作。没有该技能时，直接核对官方要求、已确认事实及实际材料，并把证据缺口列入审核包。

交接时核对实际附件内容与版本，不凭文件名认定最新。新简历与旧作品集分别记录，保留原件；尚未确认的任职关系、项目上线状态、效果数字或工作授权不能补写为事实。只有材料发生变化或已有证据冲突时重做相关检查。

## 填写与验证

1. 复用已授权事实，集中询问真正缺失且影响填写的事项；等待回答时完成其他独立工作。
2. 上传正确附件后核对文件名；如网站自动解析覆盖表单，逐项检查姓名、学历、时间及经历类型。
3. 写入后触发失焦或网站保存，并读取实际显示值。清空失败时检查状态再换支持的输入方法，不反复盲填。
4. 遮罩电话或邮箱、下拉选项在文本读取中缺失时，以页面截图核实，不据空文本认定没填。
5. 检查链接。失效的可选项目链接可以清空并记录；不可用首页冒充具体项目案例。必需作品缺失时明确阻碍。
6. 保留尚未提交的申请页面；不要为核验随意刷新草稿。只有观察到保存证据才能称服务端已保存。

## 交给本人审核

先完成能独立处理的修改，再提供简短对照：公司、岗位、地点、材料版本、重要选择、未决项及实际页面入口。说明匹配优势与证据缺口，不保证顶级匹配、ATS通过或面试。

用户只授权准备时停在可审页面。已有该岗位有效提交授权、没有未决事实、符合当前工具要求时继续提交，不再索要同一授权。法律条款、验证码等仍按使用工具的要求处理。

## 提交后的证据闭环

- 提交后寻找成功页、申请中心状态或对应回执。没有证据时记“结果待核验”，先查状态再考虑重试，避免重复申请。
- 通用测评提醒不是已获测评邀请；实际测评、补件、期限与提交成功分别记录。需本人独立完成的任务交给本人。
- 回执核验后，按下节规则解析并更新用户指定跟进主表，再归档。同步受阻时仍可归档已确认材料，但必须保留未同步状态。
- 归档实际提交件，记录来源、版本、SHA256、真实提交日期／时区及回执。没有精确时分时不要拿复核时间冒充提交时间。
- 更新岗位档案、当前行动与更新记录。每项有状态、最近核验日、下一动作及负责人；依当前授权处理后续监测，不凭本技能自动建立定时任务。

## 指定主表：解析、核验、写入、回读

主表地址仅来自用户当前明确指定或其私人工作区配置，不能硬编码到公开技能。用户最新明确指定覆盖旧配置、历史摘要和旧选岗清单；读取消息时保留完整链接中的 spreadsheet ID 与 gid，不将文档ID、标签标题和gid混用。私人配置的最小约定和虚构示例见 [references/tracker-config.md](references/tracker-config.md)。本技能不自动修改私人配置；若其他任务负责配置，交接最新目标及旧配置冲突。

写入前完成以下核验，任何不一致都停止在线写入，保留本地待同步项：

1. 从最新指定目标解析 spreadsheet ID 和 gid。缺失gid且存在多个标签时读取元数据并明确目标，不能默认第一个标签。没有明确主表时询问；不得把旧选岗清单作为替代目的地。
2. 读取实际文档元数据与目标标签，核对 spreadsheet ID、gid、文档标题、标签标题和列名。与私人配置或用户指定不符时说明具体差异；不因标题相似就写入，也不静默更改配置以通过核验。用户已明确更换主表时使用新目标，旧配置标为过期；新目标缺少标题/列映射时先读取建立映射，有歧义再询问。
3. 读取目标行，按公司＋官方岗位ID查重。同名公司不同岗位分别处理。唯一匹配更新原行；零匹配且用户已授权维护该主表时新增；多行匹配先厘清，不任意选行、合并或继续追加。岗位ID缺失时保留待匹配，不只凭职位名称猜行。
4. 定点写入已核验状态、证据来源、材料版本、下一动作及真实日期，遵循实际列映射，保留公式、数据验证、日期类型和无关单元格。不为适配记录重建整表。
5. 从同一 spreadsheet ID、gid 和实际写入范围回读，与预期逐项比较。只有一致才记“已同步”。写入报错或超时记“待核验/未同步”，先回读再决定是否重试；回读不一致记录差异，不盲目覆盖或重复追加。提交成功、表格同步和归档成功分别记录。

记录本次目标来源、文档/标签身份、实际范围、回读结果和待办到私人交接记录，公开示例只保留虚构值。表格不可访问时不回退写旧表。

## 跨任务交接

使用任务工具定位用户指定的准确任务，读取必要近况后发送交接。交接应包含：技能路径、相关档案路径、已完成项、未完成项、每岗提交权限、所需用户输入和验收标准。不得假称目标任务已完成；消息送达、对方接手、产物完成与远端发布分别验证。

浏览器草稿如由另一任务占用，不强行接管或重建；先协调页面归属或仅处理文件。公共技能与私人岗位记录分开，公开版本不含个人身份、联系方式、表格ID、私有回执或公司内部材料。GitHub发布范围与目标仓库依实际用户授权核验，不因任务标题包含GitHub就自动公开。

## 验收场景

- 公司A已批准、B待审：只提交A；B保持草稿，分别记录。
- 页面显示旧PDF、新简历已上传：旧作品集仍需单独核对，不称全部最新。
- 提交后网络错误：查申请状态，不盲目再次点击。
- 线上表写入失败：本地记录成功提交及待同步事项，不把全部闭环标为完成。
- 技能交接已送达：只报告已交接；发布后需远端链接或提交证据才能称已发布。

- 用户最新主表与旧选岗清单冲突：使用最新目标；旧表不写入。
- spreadsheet ID正确但gid不符、标题/列映射不符：停止写入并报告具体差异。
- 同公司不同岗位、重复公司＋岗位ID行：前者分别匹配；后者先消歧，不追加重复行。
- 写入超时但回读已正确：标记已同步，不重复追加；回读失败或不一致不标成功。
